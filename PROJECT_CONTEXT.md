## Design system

`app/globals.css` `@theme inline` block defines colors (`--color-primary/secondary/tertiary` + `-container`/`on-*` variants), spacing (`xs/sm/md/lg/xl/gutter/margin`), type scale (`label-sm/md`, `body-md/lg`, `headline-md/lg`, `display-lg`), fonts (`Inter` sans, `Merriweather` serif).

**Gotcha (cost real debugging time):** because the theme block uses `@theme inline` (not plain `@theme`), Tailwind bakes the *literal resolved value* into each generated utility class instead of keeping a `var(--text-display-lg)` reference. This means overriding `--text-display-lg` etc. in a later CSS rule **does nothing** — the utility classes already have `font-size: 3rem` hardcoded. To make type scale responsive, `globals.css` now has a `@media (max-width: 640px)` block that targets `.text-display-lg` / `.text-headline-lg` / `.text-headline-md` **by class name directly** (unlayered CSS beats Tailwind's `@layer utilities` regardless of source order, so no `!important` needed). Keep this in mind before trying to theme anything else via CSS variables in this file.

Article body typography is centralized in `.article-editor`/`.article-content` classes so the Tiptap editor and rendered article match.

### Community trust score formula (2026-07-27)

`resources.community_trust` is computed by the Postgres function `calculate_community_trust(target_resource_id)` (no `security definer`, plain `plpgsql`, triggered on the resource's own like/download changes and on the author's `author_trust_score` changing) — **not** the simple "40% author + 30% likes + 30% downloads" description that was in this doc before; that was stale. The real formula is a **Bayesian shrinkage blend**:

```
like_component     = least(100 * ln(1 + like_count) / ln(1 + 50), 100)       -- log-scaled, capped
download_component = least(100 * ln(1 + download_count) / ln(1 + 100), 100)  -- log-scaled, capped
community_score    = 0.4 * like_component + 0.6 * download_component
engagement_volume  = like_count + download_count
confidence         = engagement_volume / (engagement_volume + 20)           -- confidence_k = 20
blended            = confidence * community_score + (1 - confidence) * author_score
trust              = round(greatest(author_score, blended))                  -- floor added 2026-07-27, see below
```

**Bug found and fixed 2026-07-27**: before the floor, `trust = round(blended)` directly. Since `blended` is a weighted average that shifts toward `community_score` as engagement grows, **more downloads visibly lowered the trust score** whenever `community_score < author_score` — e.g. a new resource from a 90-trust author starts at `trust ≈ 90` (confidence ≈ 0 with no engagement yet), and as downloads come in the score drifts toward the resource's own (lower) engagement-derived score before eventually climbing past it once `community_score` itself overtakes `author_score`. Real, reproducible dip, not a data bug — confirmed against the live function body (`pg_get_functiondef('calculate_community_trust'::regproc)`).

**Fix**: `trust := round(greatest(author_score, blended))` — engagement can now only push the score up from the author's baseline, never below it. **SQL was handed to the user to run in the Supabase SQL editor; likely applied** (a follow-up report — "downloaded a 50-author-trust resource 10 times, still shows 50%" — is exactly the expected post-fix behavior, since `confidence_k = 20` means ~50 downloads are needed before `blended` even crosses back above a 50 baseline with zero likes) but **not explicitly confirmed run**. If `community_trust` is ever observed *decreasing* as likes/downloads increase, this fix hasn't landed — re-fetch the live function body before assuming it has.

**Open, unresolved as of 2026-07-27**: whether the current tuning (`confidence_k = 20`, log caps at like_count=50/download_count=100) is too insensitive — a resource can take dozens of downloads before `community_trust` visibly moves at all for a mid-trust author, which may or may not be the desired UX. Not changed pending the user's input; asked them to confirm the resource's actual `download_count` to rule out the trigger not firing at all, but the question was interrupted/dismissed — still open.

A different architecture was discussed and explicitly declined by the user: making `community_trust` pure engagement (no author blending at all) and deriving `author_trust_score` as an average of the author's own resources' scores (inverting today's one-directional dependency). Tradeoff flagged: it would make new resources start at 0% trust regardless of who posted them, and would make the existing admin-editable `author_trust_score` field in `/admin/users` pointless (would get overwritten on the next engagement change). **Decision: keep the current architecture** (author score as an independent admin-set prior, resources blend toward it) — just with the floor fix above.

### Retention tracking — `users.last_active_at` (2026-09 session, new)

Built to answer "how do I know if visitors come back" — Vercel's built-in Web Analytics (which the user enabled directly in the Vercel dashboard, see "Vercel Fluid CPU cost investigation" below) is deliberately privacy-first with no persistent visitor id, so it structurally can't report returning-vs-new visitors. For **logged-in** users this app already had a much better signal available for free.

Designed explicitly to add near-zero cost, given the session's whole CPU-cost context:
- `proxy.ts` gates the write on a cookie (`la-ping`, ~24h maxAge), not a DB read — so the throttle check itself never touches the database. A user with 50 page views in a day still costs exactly **one** write, not 50.
- The write itself runs via `event.waitUntil(...)` (Next's background-work API for middleware) so it never adds latency to the response the user is actually waiting on, and a swallowed `.catch()` means a missing column/grant fails silently rather than breaking navigation.
- Only fires for real navigations — the existing prefetch early-return in `proxy.ts` (see Auth section below) already skips this path for prefetches.

`app/admin/page.tsx` shows two new stat cards, "Active Users (7 days)" / "Active Users (30 days)", computed in `getAdminAnalytics()` from simple count queries against `last_active_at`.

**SQL needed (column + self-service grant), status unclear — verify before trusting the stat**:
```sql
alter table public.users add column if not exists last_active_at timestamptz;
grant update (last_active_at) on public.users to authenticated;
```
This was handed to the user during the session, but with heavy context-compaction across such a long session there's no explicit "ran it" confirmation on record. If "Active Users" shows 0 or looks obviously wrong, check this first.

### RLS/grants gotcha (bit us more than twice now)
`resources` had proper GRANT + RLS from the start. `articles` and `discussions` did not initially — same fix pattern:
```sql
grant usage on schema public to authenticated, anon;
grant select, insert, update, delete on public.<table> to authenticated;
grant select on public.<table> to anon;
-- plus RLS policies scoped to author_id = auth.uid() (or the admin id)
```
Separately, **column-level grants** restrict which fields are writable even when RLS allows the row update — `users.is_pro`/`users.author_trust_score` are deliberately excluded from the client grant (only `display_name`/`ib_year`/`bio`/`avatar_url` are writable by `authenticated`). If a new admin-only field needs writing, it needs the **service-role client**, not just an `isAdmin()` check with the regular client — the regular client will get a real Postgres permission error regardless of RLS.

## Search — resources, articles, community (2026-09 session, new)

Keyword search, not substring search: the query is split on whitespace and every word must appear in the title, in any order (`"IA Chemistry"` matches "Chemistry IA Template"). Shared helper `splitKeywords()` in `app/lib/validation.ts`, chained as `.ilike("title", "%word%")` per word (Supabase/PostgREST ANDs chained filter calls automatically) for Resources and Articles.

- **Resources/Articles**: plain code change, `getResourcesPage`/`getArticlesPage` gained a `search` filter, `resources-grid.tsx`/`article-grid.tsx` gained a debounced search input (reuses the existing 300ms-debounce pattern, see "Established code patterns").
- **Community/Discussions**: harder, since sorting/pagination there already goes through the `get_discussions_page`/`count_discussions` Postgres RPCs (see the 2026-07-21 pagination work) rather than a plain `.order()`. Both RPCs gained a new **trailing** `p_search text default null` parameter (appending rather than replacing existing params — Postgres's `CREATE OR REPLACE FUNCTION` only replaces a function if the argument *types* match exactly; a genuinely different parameter list creates a second overloaded function instead of replacing the first). **This bit us for real**: the first version of this fix used `CREATE OR REPLACE` naively and left the *old* 6-arg/3-arg versions of both functions still present alongside the new 7-arg/4-arg ones, which made PostgREST unable to pick a candidate for the call sites (`getTrendingDiscussions()`) that don't pass `p_search` — `"Could not choose the best candidate function"` error, live in production. Fixed by explicitly `DROP FUNCTION`-ing the old-signature versions once the new ones existed, plus a `NOTIFY pgrst, 'reload schema'` for good measure. **If you ever need to add a parameter to a Postgres RPC function again, drop the old-signature version explicitly — don't assume `CREATE OR REPLACE` alone removes it.**
- Search matching inside the RPC uses `title ilike all (array(select '%'||w||'%' from unnest(regexp_split_to_array(trim(p_search), '\\s+')) as w))` — same keyword-AND semantics as the plain-table version, expressed as a SQL array check since a Postgres function can't easily reuse the TS `splitKeywords()` helper.
- **Performance note (asked about by the user, answered, not acted on)**: `ilike '%word%'` can't use a normal btree index (leading wildcard), so it's a sequential scan per keyword — irrelevant at this app's current scale (~100-200 rows) but would want a `pg_trgm` GIN index on `title` if the table grows into the thousands. Not built pre-emptively.

## Vercel Fluid CPU cost investigation (2026-09 session — significant chunk of this session)

The user hit **100% of the Hobby-plan Fluid Active CPU quota** (4h/period) with the site still up, prompting a real investigation rather than a guess-and-check pass. Diagnosed using the Vercel dashboard's own breakdowns (Type/Runtime/Projects tabs) rather than assumption, and corrected course at least once when data contradicted an earlier hypothesis — worth reading in order if this comes up again, since the *wrong* theories are as informative as the right one:

1. **First hypothesis (partially right, real fix, but not the dominant cause): `next.config.ts`'s `headers()` was matching `/(.*)`** — every request including every static JS/CSS/font/`/_next/image` request, not just page loads. Fixed by scoping the `source` pattern to exclude `_next/static`, `_next/image`, `favicon.ico` (verified live via `curl` that a real page still gets the CSP header, a static chunk doesn't). Real, but the Type breakdown later showed `middleware` and `function` invocation counts almost exactly 1:1 (not the 10:1+ you'd expect if middleware were mainly catching sub-resources), which pointed at something else being the dominant driver.
2. **Second fix: `NotificationBell`'s 30-second poll ran for every open tab regardless of visibility.** A background/idle tab has no user to notify — this was pure waste scaling with "tabs left open," not real usage. Fixed with the Page Visibility API: pauses the interval entirely while `document.visibilityState !== "visible"`, does one immediate catch-up poll when it becomes visible again. Verified the start/stop/no-double-interval logic in an isolated Node simulation (no way to visually test without login credentials).
3. **The real dominant cause, found by actually reading `proxy.ts` (which had been missed earlier in the session — searched for a file named `middleware.ts`/`middleware.ts` and concluded none existed, without checking for the renamed `proxy.ts` convention at the repo root):** the middleware called `supabase.auth.getUser()` (a real network round trip to Supabase's Auth server) on **every** page navigation, and separately, `getCurrentUser()` — called by `AuthNav` in the root layout, i.e. on **every single page** — did its own independent `getUser()` call. Two full Auth-server round trips per page view, for every visitor including anonymous ones. This directly explained the earlier 1:1 middleware:function invocation ratio (both were doing the same work, once each). Fixed by having `proxy.ts` forward its already-validated result downstream via a request header for `getCurrentUserId()` to read for free — see the Auth section above and the `proxy.ts` entries there for the full mechanism, including the later further optimization to `getClaims()` (local JWT verification) and skipping prefetch requests entirely, both done by the user directly between turns on their own further passes at the same file.
4. **Tried, then explicitly reverted at the user's request**: `@vercel/analytics` + `@vercel/speed-insights` were added to the root layout for traffic analytics, which required also updating the CSP to allow `va.vercel-scripts.com`/`vitals.vercel-insights.com` (they don't load same-origin, contrary to an initial assumption — caught via a live CSP-violation console error in the dev browser). **The user enabled Web Analytics directly in the Vercel dashboard instead** and asked for the package/CSP changes to be reverted — confirmed reverted to exact zero diff against the pre-change `layout.tsx`/`next.config.ts`/`package.json` before committing anything else. **If "add analytics" comes up again, check whether Vercel's dashboard-native Web Analytics is already enabled before reaching for the npm package** — it may already be handled outside the codebase.

**Verification note**: none of items 1–3 could be confirmed to have actually reduced the Vercel dashboard's numbers within this session (the usage charts only reflect full days *before* the fix), so treat "this should help" as reasoned-but-unverified until a subsequent session can compare a full day's numbers before vs. after.

### Real server-side pagination — the big one
All three main listing grids (`/resources`, `/articles`, `/community`) used to fetch **every published row** unbounded on every page load and do filter/sort/pagination entirely client-side with `.slice()` — the page-number buttons only controlled what rendered, not what was fetched. Rewritten to filter/sort/paginate in the query itself:

- **Resources**: `getResourcesPage()` in `resources.ts` — plain `.eq()`/`.order()`/`.range()`, `{count: "exact"}` for total pages. `getResourcesWithUserState()` (old, unbounded) is kept only for the homepage's simple `{limit: 6}` featured-resources call.
- **Articles**: `getArticlesPage()` in `articles.ts`, same shape. The old unbounded `getArticlesWithUserState()` was fully replaced and **deleted** (nothing else called it). - **Community/Discussions**: the hard one — "Hot" sort is a computed formula (`like_count + reply_count / (daysOld+2)^1.5`), not a plain column, so it can't be a normal `.order()`. Added two Postgres functions (SQL below, **must be run by the user**): `get_discussions_page(...)` and `count_discussions(...)`, called via `.rpc()` from `getDiscussionsPage()` in `discussions.ts`. Old `getDiscussionsWithUserState()` (unbounded) was deleted. - All three grid components (`resources-grid.tsx`, `article-grid.tsx`, `community.tsx`) now hold only the current page in state, fetch a new page via the corresponding action on any filter/sort/page change (client components calling server actions directly), and skip the redundant duplicate fetch on mount via an `isFirstRender` ref (page 1 was already fetched server-side and passed in as `initialItems`).
- Numbered pagination UI was kept as-is (not switched to "Load more") — that was a deliberate choice, see git history if reconsidering.
- **DB indexes**: added on every column now actually filtered/sorted/joined on — `published`/`subject_tag`/`type_tag`/`year_tag`/`author_id`/`created_at`/`download_count`/`like_count` on `resources`; equivalent on `articles`/`discussions`; every FK column on `likes`/`comments`/`saved_items`/`discussion_replies`. SQL below, **must be run by the user**, uses `if not exists` so it's safe to re-run.

**SQL to run** (discussions pagination RPCs):
```sql
create or replace function get_discussions_page(
  p_subject text default null, p_type text default null, p_year text default null,
  p_sort text default 'newest', p_limit int default 6, p_offset int default 0
)
returns setof discussions language sql stable as $$
  select * from discussions
  where (p_subject is null or subject_tag = p_subject)
    and (p_type is null or type_tag = p_type)
    and (p_year is null or year_tag = p_year)
  order by
    case when p_sort = 'hot' then
      like_count + reply_count / power(extract(epoch from (now() - created_at)) / 86400 + 2, 1.5)
    end desc nulls last,
    created_at desc
  limit p_limit offset p_offset;
$$;

create or replace function count_discussions(
  p_subject text default null, p_type text default null, p_year text default null
)
returns bigint language sql stable as $$
  select count(*) from discussions
  where (p_subject is null or subject_tag = p_subject)
    and (p_type is null or type_tag = p_type)
    and (p_year is null or year_tag = p_year);
$$;

grant execute on function get_discussions_page to authenticated, anon;
grant execute on function count_discussions to authenticated, anon;
```
(Index SQL is long — see git history of this file's commit for the full script, or regenerate: every FK/filter/sort column across `resources`/`articles`/`discussions`/`likes`/`comments`/`saved_items`/`discussion_replies`.)

## Established code patterns

- Server actions live in `app/lib/actions/{resources,articles,discussions,upload,profile,saved-items,likes,comments,admin,feedback,notifications}.ts`, all `"use server"`, all return `ActionResult<T> = {success:true,data:T} | {success:false,error:string}`.
- Create/edit forms are client components. `SortDropdown`/`FilterDropdown` are plain `<button>`-based, not native inputs — value goes in via `formData.set(...)` in the submit handler, validated manually, internal buttons need `type="button"`.
- Edit routes reuse the create form component with an optional prefill prop.
- Delete buttons: `confirm()` guard → call action → `router.push()`/`router.refresh()` on success.
- Card/panel components accept an optional `href` prop to override the default detail-page link (e.g. Drafts tab → edit page instead of the 404-prone detail page).
- `next/image` with `fill` needs an explicit `sizes` prop.
- `next.config.ts`: `experimental.serverActions.bodySizeLimit: "20mb"`, `allowedOrigins` for tunneling (see Auth section). **Changing `next.config.ts` requires a dev server restart.**
- **Server-side validation**: `app/lib/validation.ts` (`requireField`/`optionalField`/`requireOneOf`) — every create/update action validates formData server-side now, not just via client "required" attributes. Use this rather than ad-hoc checks for any new form field.
- **Rate limiting**: `checkRateLimit(kind, identifier)` from `app/lib/ratelimit.ts` — call after the auth check, before doing the write, in any new action that creates content or is otherwise abusable. No-ops until Upstash env vars are set.
- **List pagination**: any new listing page should follow the `get<Thing>Page(filters)` pattern (see Resources/Articles/Discussions, and now the admin Users/Content/Feedback tables too) — filter/sort/paginate in the query via `.range()` + `{count: "exact"}`, return `{items, totalCount}`, never fetch-all-then-slice client-side. If the sort needs a computed/derived score (like Discussions' "Hot", or the homepage's "Featured Resources"), it needs a Postgres function, not a plain `.order()`.
- **Debounce listing-page fetches, don't try to cancel them (2026-07-27)**: every client-side listing component that fetches a new page on filter/sort/pagination change (`resources-grid.tsx`, `article-grid.tsx`, `community.tsx`, and now the admin tables) wraps the fetch in a `setTimeout(..., 300)` inside the `useEffect`, clearing the previous timeout in the cleanup — a real production bug (`TypeError: Failed to fetch`, verified via a controlled browser test: 5 rapid clicks → 1 request after the fix, vs. 5 before) came from rapid clicks each firing their own concurrent Server Action POST with nothing stopping them piling up under Vercel's concurrency limits. **`AbortController` cannot fix this** — verified directly against this Next 16 version's client runtime (`app-call-server.js` → `server-action-reducer.js`): calling an imported `"use server"` function directly (not via `<form action>`) goes through Next's internal `fetch()` with no `signal` parameter exposed anywhere, and there's no public API to cancel an in-flight action call. If a future listing page has this same shape, debounce the trigger — don't reach for AbortController, it doesn't exist here.
- **`<form action={fn}>` with a plain client function can silently eat your loading state (2026-07-27)**: React 19 treats a plain function passed to a form's `action` prop as a transition, and transitions are allowed to skip painting intermediate state entirely if the whole thing resolves quickly enough (an anti-flicker heuristic) — so `setStatus("saving")` etc. might never actually paint before the next state update lands, and a spinner/status text that's provably correct in code review can still never visibly appear. Bit literally every form in the app that used this pattern (login, signup, forgot/reset password, profile edit, resource upload/edit, write article, write discussion) — all fixed by switching to a plain `onSubmit` handler with `e.preventDefault()` and building the `FormData` manually (`new FormData(e.currentTarget)`, or `new FormData(e.currentTarget, submitter)` for a form with multiple named submit buttons like WriteArticleForm's Save Draft/Publish, to preserve which one was clicked). **Any new form needing a visible pending/loading state must use `onSubmit`, not `action={aPlainFunction}`** — the latter is fine for zero-feedback fire-and-forget cases, but not when you need the UI to reliably reflect "in progress."
- **New pages need their own `metadata`/`generateMetadata`** (title, description, `alternates.canonical`) — the root layout only provides defaults/fallbacks now, it doesn't mean every page should skip setting its own. Dynamic detail pages use `generateMetadata()` with the same fetch the page component uses (accepted as two DB calls per request rather than risk wrapping a `"use server"`-file export in React's `cache()`, which may not satisfy Next's Server Actions compiler — see the `SEO` section for why that was tried and reverted).
- **JSON-LD**: use `components/JsonLd.tsx` (`<JsonLd data={...} />`), never hand-roll a `<script type="application/ld+json">` — it handles the `<` escaping needed since this data often includes user-submitted content.
- **Default to `getCurrentUserId()`, not `getCurrentUser()`, for any new "is someone logged in" check (2026-09 session)** — the former reads a free request header `proxy.ts` already sets, the latter does a real Supabase network call. Reach for `getCurrentUser()` only if you need an actual Auth field beyond the id (e.g. `email_confirmed_at`). See the Auth section.
- **A Postgres RPC function's parameter list can't be changed with a plain `CREATE OR REPLACE FUNCTION` (2026-09 session, bit us in production)** — Postgres only replaces a function if the parameter *types* match exactly; adding/removing a parameter creates a second overloaded function alongside the old one, and PostgREST can then fail to pick a candidate for callers using the old signature (`"Could not choose the best candidate function"`). If a table function ever needs a new parameter, `DROP FUNCTION <name>(<old signature>)` explicitly once the new one exists, and `NOTIFY pgrst, 'reload schema'` after. See "Search" section for the real incident.
- **Toasts/popups triggered from inside a card need to be portaled to `document.body`, not positioned relative to their trigger (2026-09 session)** — several resource/article card wrappers use `overflow-hidden` (for rounded corners), which silently clips anything absolutely-positioned that pokes past the card's edge. `createPortal(..., document.body)` + `position: fixed` sidesteps this entirely, at the cost of losing the "anchored right above this specific button" placement (acceptable for a short-lived toast). See the `DownloadButton` login-prompt and `resources-grid.tsx`'s EE-exemplar disclaimer for the pattern.
- **`window.open()` after an `await` gets blocked by Safari specifically** — Safari only trusts `window.open()` as user-initiated if it's called synchronously inside the click handler. If a click handler needs to `await` a server action before knowing the URL to open, call `window.open("", "_blank")` *before* the await to grab a trusted tab handle, then set `.location.href` on it once the URL is known. Chrome/Firefox don't need this; don't skip it just because it works fine in whichever browser you're testing in.
- **`line-clamp-N` and an explicit `height`/`min-height` on the same element fight each other** — combining them can let a partial extra line bleed past the clamp boundary instead of cleanly truncating. Use `line-clamp-N` alone; if you need consistent row heights across a grid of cards with varying title lengths, that's a tradeoff to accept, not something to force with a height class.
- **Chart colors are not the same job as UI colors** — the app's `--color-primary`/`-secondary`/`-tertiary` brand hues fail categorical-chart-safety checks (too dark / too low-chroma to distinguish as chart series, confirmed with the `dataviz` skill's validator). Any new chart needs its own validated palette (see "Admin analytics dashboard" section for DiplomaHub's specific validated triplet) — don't just reuse the brand CSS variables for chart marks.

### The same root cause bit us twice — Supabase Redirect URLs allowlist

After forgot-password shipped (see below), a real reset-link click landed on `https://www.diplomahub.org/?code=...` — the **bare homepage**, not `/auth/reset-password`. Root cause: Supabase silently ignores any `redirectTo` that isn't in its **Redirect URLs allowlist** (Authentication → URL Configuration) and falls back to the plain **Site URL** instead — exactly the same failure mode that broke Google OAuth login earlier in the project's history (that time it was `/auth/callback` missing from the allowlist; this time `/auth/reset-password` was missing, because it didn't exist yet when the allowlist was last configured). Given this exact bug class has now recurred once, a wildcard (`https://www.diplomahub.org/auth/**` + `http://localhost:3000/auth/**`) is worth doing instead of exact-path entries, so any *future* route added under `/auth/` doesn't need another manual dashboard trip. **Not confirmed whether the user actually applied this fix** — if a fresh password-reset link still dead-ends on the homepage, check this allowlist first before assuming a code bug.
